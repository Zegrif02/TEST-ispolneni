# План проверки API исполнений

## Этап 1 — чтение (подтверждён на КОМПАС-3D v25)

- Подключение к уже запущенному КОМПАС через ROT.
- Получение активного документа.
- Загрузка зарегистрированной TypeLib API7 через `LoadRegTypeLib`.
- Поиск IID `IKompasDocument3D` и `IEmbodimentsManager`.
- Получение `IEmbodimentsManager` через `QueryInterface`.
- Чтение количества исполнений и обозначений по индексам.
- Успешно прочитаны отдельные значения базы, номера исполнения и полного обозначения.

## Этап 2 — контролируемая запись и однократное перестроение (версия 0.2.1)

Цель: проверить на отдельной одноразовой копии, что `SetEmbodimentMarking(index, ksVMBaseMarking, newBaseMarking)` меняет базовую часть, не меняя номер исполнения.

Условия:

1. Исходный рабочий документ закрыт.
2. В КОМПАС открыта отдельная тестовая копия, которую можно без сожаления закрыть без сохранения.
3. Выполнено свежее чтение активного документа.
4. Выбрано обычное исполнение с непустым номером, например `-02`; варианты геометрии для первого теста исключены.
5. Введено новое базовое обозначение, отмечена тестовая копия, введено слово `ИЗМЕНИТЬ` и принято финальное предупреждение.

Перед вызовом программа ещё раз проверяет путь документа и старые значения базы, номера и полного обозначения. Затем вызывает `SetEmbodimentMarking` для выбранного индекса. Сразу фиксирует промежуточные значения, которые могут оставаться старыми. После этого один раз вызывает `IKompasDocument3D.RebuildDocument()`, закрывает старые COM-ссылки, повторно подключается через ROT и считывает все исполнения заново.

Успех подтверждается только если:

- новая базовая часть совпала с введённой;
- номер исполнения побайтно/посимвольно совпал со старым значением;
- полное обозначение совпало с `новая база + исходный номер исполнения`.

Дополнительно проверяется, что все остальные исполнения остались неизменными. `Save` не выполняется. В версии 0.2.1 один `RebuildDocument` выполняется намеренно как предмет отдельного эксперимента. После теста закрыть копию без сохранения.

## Этап 3 — анализ результата

По новому логу подтвердить реальное поведение API. Только после этого обсуждать перенос подхода в DesignationEditor2. Никакой код основной программы этим тестом не меняется.


## Этап 3 — проверка одного перестроения

Критерий положительного результата: `RebuildDocument` вернул TRUE, после нового подключения базовая часть целевого исполнения равна введённой, номер и полное обозначение совпадают с ожидаемыми, а все остальные исполнения остались без изменений. Если метод вернул FALSE, вызвал COM-исключение или контрольные значения не совпали, результат считается неполным/неуспешным; файл не сохранять.
